① 今日の主役

UML での意味

言葉意味
UMLUnified Modeling Language（統一モデリング言語）。ソフトウェアの構造や動きを図で表すための、世界共通の描き方。クラス図・ユースケース図・シーケンス図など、目的ごとに図の種類が決められています。
ユースケースシステムを使う人（アクター）から見た、システムでできること1つ1つ。「商品を登録する」のように「〜を〜する」で表し、ユースケース図では楕円で描きます。
ユースケース記述1つのユースケースについて、主アクター・事前条件・事後条件・基本フロー・代替フローを文章で書いたものです。
シナリオユースケースの流れを、具体的な人や値を入れた「ある1回分」の話として書いたものです。

たとえで言うと

ユースケースは「メニューの1品」、UML は「世界共通の描き方」

メニューには、お客が頼めることだけを書きます。厨房の手順は書きません。

メニューには、お客が頼めることだけを書く。ユースケース図も同じ

喫茶店のメニューには「ブレンドコーヒー」「ケーキセット」と、お客が頼めることが並んでいます。豆の挽き方や、厨房の手順は書いてありません。

アプリも同じです。使う人（担当者）から見て「このアプリでできること」を1つずつ書き出したものがユースケースです。商品在庫管理アプリなら「商品を登録する」「商品を売る」などです。中でどんなクラスが動くかは書きません。

描き方も決まっています。使う人は棒人間、できることは楕円、作る範囲は四角です。こうした図の描き方を世界共通に決めたものが UML（Unified Modeling Language、統一モデリング言語）です。会社や国が違っても、同じ図が同じ意味に読めます。

第10〜14回は、コードを書いてアプリを作りました。今日から第19回までは、そのアプリを UML の図で描きます。

1品ごとの作り方のカードがユースケース記述、ある日の1回分の流れがシナリオ

メニューの1品ごとに、作り方のカードがあります。注文を受けてから出すまでの手順と、品切れのときの対応が書いてあります。アプリでは、これがユースケース記述です。

「ある日、お客がブレンドを1杯頼んだ」のように、実際の1回分の流れを書いたものがシナリオです。

なぜ必要か

UMLプログラムの形や動きを、言葉より正確に、誰が見ても同じ意味で伝えるためです。
ユースケース作る前に「このアプリで何ができればよいか」を、使う人の目線で漏れなく決めるためです。
ユースケース記述図の楕円1つでは分からない、操作の手順と、うまくいかない場合の動きを決めておくためです。
シナリオ手順を具体的な例で確かめ、抜けや食い違いを見つけるためです。

今日のゴールは、このアプリのメニュー（ユースケース図）と、そのうち1品の手順書（ユースケース記述とシナリオ）を描けるようになることです。まず写します。

③ 解説（要点だけ読む）

結論と短い例だけで確認できます。図や詳しい説明は必要な項目だけ開いてください。

どの図でも使う書き方

UMLの「ノート」は図の補足。«include»などの文字は関係や種類を表す。

«include» / «extend»

この部分のコード・詳しい説明を見る
記号・書き方名前意味と書き方
ノート右上の角を折った四角です。図だけでは書けない補足・前提・決まりを書き、説明したい所と破線で結びます。
«include» «interface» «create»ステレオタイプ« » で囲んだ言葉です。線や箱の種類を言葉で書き足す印で、どの図にも出てきます。手で書くときは <<include>> でも構いません。
{readOnly} {ordered}制約{ } で囲んだ決まりです。{readOnly} は書き換えない（Java の final）、{ordered} は順番がある、という意味です。

1　アクターと関連（①②）

アクターは操作する『人や外部システムの役割』。線でできることと結ぶ。

担当者 ── (商品を検索する)

この部分のコード・詳しい説明を見る

① 棒人間（アクター）

①の棒人間がアクターです。アクターは、システムの外にいて、システムを使う相手のことです。

棒人間の下の「担当者」は、役割の名前です。山田さんのような人の名前ではなく、役割を書きます。人だけでなく、会計システムのような外のシステムもアクターになります。「毎月末」のような時間もアクターになります。

なぜ描くのか。誰のために作るのかを、はっきりさせるためです。

② 担当者から楕円への実線（関連）

②は、担当者の手元から楕円へ伸びる実線です。これが関連です。関連は「この人が、これを使う」という意味です。

線は、6つの楕円すべてに引いてあります。担当者は6つとも使える、ということです。関連の線には、矢印を付けません。線の無い楕円は、誰も使わない機能ということになります。

線が横切る縦の線は③のシステム境界、右の楕円は④のユースケースです。

よくある間違い：MySQL をアクターにする。「データは MySQL にしまうから、MySQL もアプリを使う相手だ」と考えた形です。四角の外に、MySQL の棒人間を描いてしまいます。四角の外にあるのは「作らないもの」です。これでは、MySQL がアプリの範囲の外にいる相手だ、と言っていることになります。

自分たちが用意したものは四角の中。外にいて、やりとりする相手だけがアクター

上の図の四角の中には、第13回・第14回で作った画面とクラス、MySQL を並べました。ProductFrame は画面、ProductService は入力の検査をするクラスです。ProductDAO は、データベースとの出し入れをするクラスです。MySQL の products 表には、商品のデータが入っています。このアプリでは、MySQL は自分たちが用意した、アプリの一部です。四角の中のものなので、四角の下に書いたとおり、ユースケース図には描きません。

図の左の担当者は、アプリを使う人なので、アクターです。右の会計システムは、よその持ち物で、このアプリとやりとりする相手です。だから、これもアクターです。反対に、担当者を四角の中に描くのも間違いです。アクターは必ず四角の外です。

見分け方置く場所例
自分たちが作る・用意するもの四角の中（図には描かない）画面、クラス、MySQL
外にいて、アプリとやりとりする相手四角の外にアクターとして描く担当者、会計システム、毎月末

アクターどうしは、汎化という線でつなぐことがあります。汎化は「店長は、店員の一種」のような関係です。子のアクター（店長）は、親のアクター（店員）のできることを全部できます。下の図では、子の店長から親の店員へ実線を引き、親の側の端に白抜きの三角を付けています。

3　ユースケース（④）

ユースケースは利用者に見える機能。『商品を登録する』など動詞で表す。

(商品を登録する)

この部分のコード・詳しい説明を見る

④ 楕円（ユースケース）

④の楕円がユースケースです。ユースケースは、アクターから見た「このアプリでできること」1つです。名前は「商品を一覧する」「商品を登録する」のように、「〜を〜する」の形にします。楕円の左の端に付いている線は、②の関連の線の先です。

なぜ使う人の言葉で書くのか。依頼した人と「これができるようになります」を確かめる図だからです。

よくある間違い：画面・操作・SQL の言葉で名前を付ける。名前は、使う人が「よし終わった」と思える単位で書きます。下の表の左の列が、よくない名前の例です。楕円どうしを矢印でつないで、画面の順番を描くのも間違いです。ユースケース図に、順番はありません。

よくない名前理由直した名前
商品一覧画面画面の名前商品を一覧する
登録ボタンを押す操作であって、目的ではない商品を登録する
INSERT する中の仕組み（SQL）の言葉商品を登録する
商品名を入力する細かすぎる。入力しただけでは用が済まない商品を登録する（その中の1手順）
商品管理名詞で、何をするのか分からない商品を登録する・商品を更新する など

楕円どうしの関係には、include と extend の2つがあります。「商品を登録する」と「商品を更新する」は、どちらも必ず入力内容を検査します。この共通の手順を、楕円1つにくくり出すのが include です。「商品を売る」とき、残りが0個になったら、売り切れを知らせるとします。このようにときどき起きることを付け足すのが extend です。

include は呼ぶ側からくくり出した側へ、extend は付け足す側から元の楕円へ

上の段の «include»

上の段では、「商品を登録する」から「入力内容を検査する」へ、破線の矢印を引いています。破線と開いた矢じり（V の形）で描きます。「登録するとき、必ず検査を呼ぶ」と読みます。

矢印の上の «include» のように、« » で囲んで書き添えた言葉をステレオタイプと言います。ステレオタイプは、線や箱の種類を言葉で書き足す印です。手で書くときは、<<include>> でも構いません。

下の段の «extend»

下の段では、「売り切れを知らせる」から「商品を売る」へ、破線の矢印を引いています。線と矢じりは include と同じで、上に «extend» と書きます。「売るときに、知らせる処理がときどき割り込む」と読みます。

includeextend
起きるのは必ずときどき（条件が成り立ったとき）
矢印の向き呼ぶ側 → くくり出した側付け足す側 → 元のユースケース
例登録するとき、必ず入力内容を検査する売るとき、残りが0個になったら売り切れを知らせる

よくある間違い：extend の矢印を、include と同じ向きに描く。「商品を売る」から「売り切れを知らせる」へ向けた形です。これでは「売るときは、必ず知らせる処理を呼ぶ」と読めてしまいます。迷ったときは、「それは必ず起きますか」と自分に聞いてください。必ずなら include、ときどきなら extend です。

includeいんくるーど必ず起きる共通の手順を、くくり出す関係。呼ぶ側から、くくり出した側へ破線の矢印
extendえくすてんど条件が成り立ったときだけ付け足される関係。付け足す側から、元のユースケースへ破線の矢印
ステレオタイプすてれおたいぷ«include» のように « » で囲んで、線や箱の種類を書き添えたもの。手で書くときは <<include>> でも構いません
汎化はんか「管理者は、担当者の一種」のような関係。子から親へ、白抜きの三角の矢印を引きます。第6回の継承と同じ考え方
ユースケース記述ゆーすけーすきじゅつ1つのユースケースの手順を、決まった項目で文章にしたもの。楕円1つにつき1枚
主アクターしゅあくたーそのユースケースを始めるアクター
関係者と関心事かんけいしゃとかんしんじそのユースケースで、誰が何を気にしているか
事前条件じぜんじょうけん始める前に成り立っていること。ここでは確かめず、成り立っているものとして進めます
事後条件じごじょうけん終わったあとに成り立っていること。完成したかどうかの判定に使います
トリガーとりがーユースケースが始まるきっかけ
基本フローきほんふろーうまくいったときの手順。主語を書き、番号を振ります
代替フローだいたいふろーうまくいかなかったときの手順。3a、3a-1 のように番号を振り、最後に行き先を書きます
シナリオしなりおユースケースを、名前と具体的な値の入った「ある1回分」の話として書いたもの。正常・異常・例外の3種類があります
要件定義ようけんていぎ何を作るか（と、何を作らないか）を決める工程。開発の最初に行います
分析ぶんせき登場する「もの」を洗い出す工程
設計せっけいどう作るかを決める工程

振る舞い図ふるまいず「どう動くか」を表す UML の図。ユースケース図・シーケンス図など
