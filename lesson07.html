インタフェース・抽象クラスとポリモーフィズム

第10章　インタフェース ／ ポリモーフィズム ／ 抽象クラス

今日の主役

インタフェース　ポリモーフィズム　抽象クラス

今日できるようになること
  • インタフェースを書き、implements でその約束を守るクラスを作れる
  • 親の型の変数・配列・引数に、種類の違うインスタンスを入れられる

① 今日の主役

Java での意味

言葉意味
インタフェースクラスが持つべきメソッドの名前・引数・戻り値の型だけを決めたもの。中身は書きません。implements したクラスは、そのメソッドを全部書かなければなりません。public interface Coupon { int apply(int price); }
ポリモーフィズム多態性。親の型（インタフェースや親クラス）の変数で同じメソッドを呼んでも、中に入っているインスタンスのクラスによって、違う処理が動くことです。Coupon c = new YenCoupon(300); c.apply(1280)
抽象クラスabstract を付けた、new できないクラスです。中身の無いメソッド（抽象メソッド）と、中身のあるメソッドを両方持てます。public abstract class Sale { public abstract int apply(int price); }

たとえで言うと

レジは、券の種類を知らなくてよい

決まった形の券なら、どれも同じ手順で通せます。値引きのしかたは券が知っています。

レジは「Coupon」としか見ていない。値引きのしかたは券が知っている

お店のレジには、割引券を通す手順が1つだけあります。10%オフ券も300円引き券も、通し方は同じです。いくら引くかは、券の側に書いてあります。

Java では、「レジに通せる券なら、名前と値引き後の金額が言える」という決まりをインタフェースとして書きます。今日は Coupon です。中身は書かず、約束だけを並べます。

レジ（使う側）は Coupon 型で受け取って c.apply(1280) と呼ぶだけです。中に入っているのが10%オフ券なら10%、300円引き券なら300円引かれます。親の型で受けると、中身（子）の動きが出る。これがポリモーフィズムです。

新しい種類の券が増えても、レジの手順は1行も変わりません。

印刷済みの欄は中身のあるメソッド、空いた値引きの欄は abstract のメソッド。台紙のままでは new できない

券の台紙には、店名や有効期限の欄は印刷済みで、値引きの欄だけが空いているものもあります。種類ごとに値引きの欄を書けば、券ができあがります。この台紙に当たるのが抽象クラスです。台紙のままでは券として使えないように、抽象クラスは new できません。

なぜ必要か

インタフェース使う側が中身の種類を知らなくても、同じ呼び方で使えるようにするためです。
ポリモーフィズム種類が増えても、使う側のコードを書き換えずに済むからです。
抽象クラス子クラスに共通の処理は親に書いておき、種類ごとに違う所だけを子に書かせたいからです。

第6回では extends で親子のクラスを作りました。今日の Coupon も「親の型」の一種で、中身を持たず約束だけを書いたものです。まず写します。

全体像

プロジェクトの中は、次の4つのファイルだけです。どれも1行目は package lesson07; です。

Coupon.java　決まり（インタフェース）

package lesson07;

public interface Coupon {                 // ① インタフェース
    String getName();                     // ② 約束（中身は書かない）
    int apply(int price);                 // ② 約束（中身は書かない）
}

PercentCoupon.java　割合で引く券

package lesson07;

public class PercentCoupon implements Coupon {    // ③ implements
    private int rate;

    public PercentCoupon(int rate) {
        this.rate = rate;
    }

    @Override                                     // ④ 約束の中身を書く
    public String getName() {
        return rate + "%オフ";
    }

    @Override                                     // ④ 約束の中身を書く
    public int apply(int price) {
        return price * (100 - rate) / 100;
    }
}

YenCoupon.java　金額で引く券

package lesson07;

public class YenCoupon implements Coupon {        // ③ implements
    private int yen;

    public YenCoupon(int yen) {
        this.yen = yen;
    }

    @Override                                     // ④ 約束の中身を書く
    public String getName() {
        return yen + "円引き";
    }

    @Override                                     // ④ 約束の中身を書く
    public int apply(int price) {
        return price - yen;
    }
}

Main.java　レジ

package lesson07;

public class Main {
    public static void main(String[] args) {
        Coupon[] coupons = {                           // ⑤ Coupon 型で受ける
            new PercentCoupon(10),
            new YenCoupon(300),
            new PercentCoupon(50)
        };

        for (Coupon c : coupons) {
            register(c, 1280);
        }
    }

    static void register(Coupon c, int price) {        // ⑥ レジ
        System.out.println(c.getName() + " : " + price + "円 → " + c.apply(price) + "円");
    }
}

③ 解説

写したコードを、行の右の番号の順に説明します。説明する所のコードを、それぞれの頭に抜き出しています。よくある間違いも一緒に見ます。

1　インタフェースに約束を書く（①②）

Coupon.java から抜き出しています。

public interface Coupon {                 // ① インタフェース
    String getName();                     // ② 約束（中身は書かない）
    int apply(int price);                 // ② 約束（中身は書かない）
}

class の代わりに interface と書いたものがインタフェースです。「Coupon を名乗るなら、このメソッドを持つこと」という約束だけを書く場所です。このコードでは、レジ（Main）は Coupon という約束だけを見ていて、券が何の種類かは知りません。レジが頼りにするのは「Coupon なら getName と apply がある」という約束だけです。

2行とも、中身の { } が無く、; で終わるメソッドです。名前・引数・戻り値の型だけを決めています。なぜ中身を書かないのか。値引きの計算は券ごとに違うので、ここでは決められないからです。中身を決めるのは、約束を守る側の各クラスです。public を書かなくても、public として扱われます。

2　約束を守るクラスを作る（③④）

PercentCoupon.java から抜き出しています。

public class PercentCoupon implements Coupon {    // ③ implements
    // （中略）
    @Override                                     // ④ 約束の中身を書く
    public String getName() {
        return rate + "%オフ";
    }

    @Override                                     // ④ 約束の中身を書く
    public int apply(int price) {
        return price * (100 - rate) / 100;
    }
}

implements Coupon は「Coupon の約束を守ります」という宣言です。extends と同じく、クラス名のあとに書きます。なぜ要るのか。これを書いたクラスだけが、Coupon 型の変数に入れられるからです。同じ名前のメソッドを持っていても、implements が無ければレジには通せません。

@Override を付けて、約束したメソッドの中身を書きます。@Override は「約束（親）のメソッドを書いています」という印で、名前の打ち間違いをエラーで知らせてくれます。YenCoupon も同じ形で、apply の中身だけが違います。

よくある間違い：約束のメソッドを書き忘れる。YenCoupon から apply を消した形です。ほかの3つは写したままです。

YenCoupon.java（間違いあり）

package lesson07;

public class YenCoupon implements Coupon {
    private int yen;

    public YenCoupon(int yen) {
        this.yen = yen;
    }

    @Override
    public String getName() {
        return yen + "円引き";
    }

    // apply を書き忘れた
}

エラーメッセージ（Eclipse）

型 YenCoupon は継承された抽象メソッド Coupon.apply(int) を実装する必要があります （The type YenCoupon must implement the inherited abstract method Coupon.apply(int)）

implements Coupon と書いた時点で、「getName と apply を持っています」と名乗ったことになります。1つでも欠けていると、レジが c.apply(...) と呼んだときに動かすものがありません。そこで Java は、実行する前にエラーで止めます。

ここで出た言葉抽象メソッド　中身の { } が無いメソッド。インタフェースに書いた約束は、すべてこれです。エラー文の「抽象メソッド」はこれを指しています実装する　約束（抽象メソッド）に、中身を書くこと
Eclipse では、クラス名の行に赤い波線が出ます。波線にマウスを乗せて「実装されていないメソッドの追加」を選ぶと、足りないメソッドの枠を自動で書いてくれます。

よくある間違い：public を付け忘れる。YenCoupon の apply から public を消した形です。ほかの3つは写したままです。

YenCoupon.java（間違いあり）

package lesson07;

public class YenCoupon implements Coupon {
    private int yen;

    public YenCoupon(int yen) {
        this.yen = yen;
    }

    @Override
    public String getName() {
        return yen + "円引き";
    }

    @Override
    int apply(int price) {                        // ここが問題
        return price - yen;
    }
}

エラーメッセージ（Eclipse）

Coupon から継承されたメソッドの可視性を下げることはできません （Cannot reduce the visibility of the inherited method from Coupon）

インタフェースに書いたメソッドは、public を書かなくても public（どこからでも呼べる）です。守る側で public を外すと、「同じパッケージからしか呼べない」に狭まってしまいます。約束より狭くすることはできないので、エラーになります。

ここで出た言葉可視性　そのメソッドを、どこから呼べるかの範囲。public や private で決まります
インタフェース側では public を省いて書き、守る側では必ず付けます。書く場所によって扱いが違うので、いちばん迷いやすい所です。

3　親の型で受ける（⑤⑥）

Main.java から抜き出しています。

public static void main(String[] args) {
    Coupon[] coupons = {                           // ⑤ Coupon 型で受ける
        new PercentCoupon(10),
        new YenCoupon(300),
        new PercentCoupon(50)
    };

    for (Coupon c : coupons) {
        register(c, 1280);
    }
}

static void register(Coupon c, int price) {        // ⑥ レジ
    System.out.println(c.getName() + " : " + price + "円 → " + c.apply(price) + "円");
}

Coupon 型の配列に、種類の違う券を混ぜて入れています。なぜ Coupon 型にするのか。親の型で受ければ、implements Coupon したクラスなら何でも入るからです。PercentCoupon[] にすると YenCoupon は入りません。

register はレジ役のメソッドです。Coupon 型で受け取り、c.apply(price) と呼びます。ここが今日の主役です。c の中身が PercentCoupon なら PercentCoupon の apply が、YenCoupon なら YenCoupon の apply が動きます。変数1つでも同じで、Coupon c = new PercentCoupon(10); の中身を new YenCoupon(300) に入れ替えれば、同じ c.apply(1280) で結果が変わります。

券の種類を足すときは、implements Coupon したクラスを作り、配列に1行足すだけです。register と for は1文字も変えません。

よくある間違い：受け取る型を子にする。レジの引数を、Coupon ではなく PercentCoupon にした形です。Main だけ変えています。

Main.java（間違いあり）

package lesson07;

public class Main {
    public static void main(String[] args) {
        register(new PercentCoupon(10), 1280);
        register(new YenCoupon(300), 1280);             // エラー
    }

    static void register(PercentCoupon c, int price) {  // ここが問題
        System.out.println(c.getName() + " : " + price + "円 → " + c.apply(price) + "円");
    }
}

エラーメッセージ（Eclipse）

型 Main のメソッド register(PercentCoupon, int) は引数 (YenCoupon, int) に適用できません （The method register(PercentCoupon, int) in the type Main is not applicable for the arguments (YenCoupon, int)）

受け取る型を子にすると、ほかの種類の券が通らない

引数を PercentCoupon にすると、このレジは「10%オフ券専用」になります。YenCoupon は PercentCoupon の仲間ではないので、渡せません。写したコードのとおり、受け取る型を親の型 Coupon にすれば、implements Coupon したクラスは全部渡せます。変数・配列・引数の型は、できるだけ親の型で書く。これが、今日の主役を使うときの基本の形です。

よくある間違い：親の型の変数から、約束に無いメソッドを呼ぶ。PercentCoupon に、割引率を返す getRate() を足しました。それを Coupon 型の変数から呼んだ形です。

PercentCoupon.java（getRate を足したもの）

package lesson07;

public class PercentCoupon implements Coupon {
    private int rate;

    public PercentCoupon(int rate) {
        this.rate = rate;
    }

    public int getRate() {                        // 足した行
        return rate;                              // 足した行
    }                                             // 足した行

    @Override
    public String getName() {
        return rate + "%オフ";
    }

    @Override
    public int apply(int price) {
        return price * (100 - rate) / 100;
    }
}

Main.java（間違いあり）

package lesson07;

public class Main {
    public static void main(String[] args) {
        Coupon c = new PercentCoupon(10);

        System.out.println(c.getName());
        System.out.println(c.getRate());               // エラー
    }

エラーメッセージ（Eclipse）

メソッド getRate() は型 Coupon で未定義です （The method getRate() is undefined for the type Coupon）

呼べるかどうかは変数の型、どう動くかは中身で決まる

中身は確かに PercentCoupon です。それでも Java は、呼べるかどうかを変数の型（Coupon）で決めます。Coupon の約束には getRate がありません。300円引き券が入っているかもしれない変数なので、呼べないのです。

割引率を聞きたいのが10%オフ券だけなら、PercentCoupon p = new PercentCoupon(10); のように子の型の変数で受けます。すべての券に聞きたいことなら、Coupon の約束に1行足します。そうすれば、どの券も書く義務を負い、Coupon 型のまま呼べます。

4　new できない親クラス　抽象クラス

インタフェースに近いものに、抽象クラスがあります。親クラスに abstract を付け、中身を書かないメソッドを混ぜたものです。「値引きのしかたは子に任せ、表示の手順は親に1回だけ書く」という例です。今日は見て違いを知るだけで、④では使いません。

Sale.java　親（抽象クラス）

package lesson07;

public abstract class Sale {                      // abstract を付ける
    private String label;

    public Sale(String label) {
        this.label = label;
    }

    public abstract int apply(int price);         // 中身を書かない（子が書く）

    public void show(int price) {                 // 中身のあるメソッドも書ける
        System.out.println(label + " : " + price + "円 → " + apply(price) + "円");
    }
}

子の側は public class TimeSale extends Sale のように extends で引き継ぎ、apply の中身だけを書きます。show は親に1回書くだけで、中の apply(price) は中身（子）の apply が呼ばれます。ここでもポリモーフィズムが働いています。

インタフェース抽象クラス
書き方public interface Couponpublic abstract class Sale
子の側implements Couponextends Sale
いくつ親にできるかいくつでも（カンマで並べる）1つだけ
書けるもの約束（中身の無いメソッド）が中心約束に加えて、フィールド・コンストラクタ・中身のあるメソッド
向いている場面「〜できる」ものを、種類を問わず集めたい共通の中身があり、「〜の一種」と言える

インタフェースと抽象クラスは、どちらも new できません。new Sale("特売") と書くと「型 Sale のインスタンスを生成できません」というエラーになります。インタフェースと抽象クラスは、変数・配列・引数の型として使うためのものです。

④ 自力で書く　1　Shipping と2種類

Shipping.java

package lesson07;

public interface Shipping {
    // ここに、名前を返す getName() の約束を書く
    String getName();
    // ここに、合計金額 total を受け取って送料を返す getFee(int total) の約束を書く
    int getFee(int total);
}

StorePickup.java

package lesson07;

public class StorePickup implements Shipping {
    // ここに getName() を書く（「店頭受け取り」を返す）
    @Override
    public String getName() {
        return "店頭受け取り";
    }

    // ここに getFee(int total) を書く（いつでも 0 を返す）
    @Override
    public int getFee(int total) {
        return 0;
    }
}

HomeDelivery.java

package lesson07;

public class HomeDelivery implements Shipping {
    // ここに getName() を書く（「宅配」を返す）
    @Override
    public String getName() {
        return "宅配";
    }

    // ここに getFee(int total) を書く（5000円以上なら 0、それより少なければ 600 を返す）
    @Override
    public int getFee(int total) {
        if (total >= 5000) {
            return 0;
        }
        return 600;
    }
}

ShippingMain.java

package lesson07;

public class ShippingMain {
    public static void main(String[] args) {
        Shipping[] list = {
            // ここに new StorePickup() と new HomeDelivery() を、カンマで区切って書く
            new StorePickup(),
            new HomeDelivery()
        };

        for (Shipping s : list) {
            show(s, 3000);
            show(s, 6000);
        }
    }

    static void show(Shipping s, int total) {
        // ここに「名前 : 合計円の注文 → 送料○円」の表示を書く
        System.out.println(s.getName() + " : " + total + "円の注文 → 送料" + s.getFee(total) + "円");
    }
}

StorePickup の getFee は total を使いませんが、引数は約束どおりに書きます。約束と引数の形が違うと、別のメソッドとみなされ、③解説の2のエラーになります。

⑤ まとめ

確認チェック

  • 「親の型で受けると、子の動きが出る」を、Coupon の例で説明できる
  • インタフェースを書き、implements したクラスで約束のメソッドを全部書ける
  • インタフェースと抽象クラスの違いを1つ言える

次回

次回は、コレクションの ArrayList と HashMap です。今日まで使ってきた配列は、作るときに個数を決めないといけません。次回はあとから何個でも足せる入れ物を扱います。そこで出てくる List は、今日のインタフェースそのものです。

用語集を確認する（必要なときだけ）

この回に出た言葉です。覚えるためではなく、分からなくなったときに引くための表です。

言葉読み方意味
インタフェースいんたふぇーす「このメソッドを持つこと」という約束だけを並べたもの。public interface Coupon { ... }。Eclipse の表示では「インターフェース」
ポリモーフィズムぽりもーふぃずむ親の型で受けて同じ呼び方をしても、中身（子）によって動きが変わること。多態性とも言います
implementsいんぷりめんつ「そのインタフェースの約束を守ります」という宣言。class PercentCoupon implements Coupon
実装するじっそうする約束（抽象メソッド）に、中身を書くこと
親の型おやのかたいくつもの種類をまとめて受け取れる型。インタフェースか、親クラス（抽象クラスを含む）で作ります
抽象メソッドちゅうしょうめそっど中身の { } が無く、; で終わるメソッド。子が必ず中身を書きます
abstractあぶすとらくと「中身がまだ決まっていない」という印。abstract class abstract int apply(...)
抽象クラスちゅうしょうくらすabstract を付けたクラス。new できず、親の型として使います。フィールドや中身のあるメソッドも持てます
@Overrideあっと おーばーらいど「親や約束のメソッドを書いています」という印。名前の打ち間違いをエラーで知らせてくれます（第6回）
extendsえくすてんず親クラスを引き継ぐ宣言。親にできるのは1つだけです（第6回）
可視性かしせいそのメソッドをどこから呼べるかの範囲。public や private で決まります
