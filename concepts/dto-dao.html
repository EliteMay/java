DTO・DAO・Serviceと3層

クラスを役割ごとに分けると何が楽になるのか。

まず結論

DTOはデータを運ぶ入れ物、DAOはDBへの保存や取得、Serviceは業務ルールを担当する。Mainや画面がSQLと業務ルールを全部持たないように分ける。

コードと結果で確認

処理の流れを先に捉えてから、各行の意味を確認しよう。

設計のイメージ（簡略サンプル）
// DTO: データの入れ物
class ProductDTO {
    int id;
    String name;
    int price;
}

// DAO: データの保存と取得（DB処理はここ）
class ProductDAO {
    void insert(ProductDTO product) {
        // JDBCでINSERTする処理
    }
}

// Service: 業務ルール
class ProductService {
    private final ProductDAO dao = new ProductDAO();
    void register(ProductDTO product) {
        if (product.price < 0) {
            throw new IllegalArgumentException("価格が不正");
        }
        dao.insert(product);
    }
}
実行結果・前提
これはクラスの役割を示す抜粋。単独では実行しない。

1行ずつ考えると

  1. Main（または画面）はProductService.registerに登録を依頼する。
  2. Serviceは価格が不正なら登録を拒否する。ルールに問題なければDAOを呼ぶ。
  3. DAOがJDBCでDBに登録する。DTOは処理の間で商品データを受け渡す。

ここで間違えやすい

よくある勘違いDTOにSQLを書いたり、Mainで直接conn.prepareStatementを大量に呼んだりすると、修正箇所が散らばりやすい。Serviceを置いただけで自動的に正しい設計になるわけではなく、責任の分担が大切。

処理がどの方向へ流れるか

比較用のコード（必要部分を抜粋）
Main → ProductService → ProductDAO → Database
        ProductDTO（商品データを受け渡す）

この矢印は呼び出しの流れを簡略化した図。ServiceがDAOを使い、DAOがDBを扱う。画面の変更やDB実装の変更で影響を限定しやすくなる。

30秒で理解チェック

価格がマイナスの商品を登録させないルールは、DTO・DAO・Serviceのどこが基本的に担当する？

答えと理由を開く

Service。 業務上の登録ルールを判定する。DBの制約も併用できるが、画面からDAOへ直接渡す前にルールをまとめる。
